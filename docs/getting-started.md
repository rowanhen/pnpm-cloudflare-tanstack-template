# Getting started

Build locally first, then connect the services you need. You can run and test the application without opening any provider dashboard. Real login, payments, analytics and email need access to an existing provider account.

## 1. Install and run

Install [Node.js](https://nodejs.org/en/download) (26.12.0, matching `.nvmrc`) and [Git](https://git-scm.com/downloads). A terminal is the app where you run the commands below. Keep it open while developing.

```bash
git clone https://github.com/rowanhen/pnpm-cloudflare-tanstack-template.git my-project
cd my-project
npm install --global pnpm@10.34.7
pnpm install
pnpm setup-project my-project
pnpm dev
```

`setup-project` is optional: it changes local package, app and Cloudflare resource names. Run it before creating cloud resources. It does not rename a GitHub repository. To start your own GitHub repository, use the repository's **Use this template** button and clone that new repository instead.

Open http://localhost:3000. Submit the waitlist with an address you control and tick the consent checkbox. You should reach `/waitlist/success`. Entries save locally; email is off until you connect it. Repeating the same address shows the same success page without creating another entry.

Open http://localhost:3001. The private dashboard redirects to `/login`. The Google button becomes available after step 3. There is no default password or hidden demo login.

Use **Ctrl+C** in the terminal to stop the apps. Local D1 (database) and R2 (file storage) persist in `apps/api/.wrangler` between runs. Test commands use separate temporary storage.

## 2. Know where the pages live

The website and dashboard are separate apps. A path belongs to the origin in this table: `/login` on the marketing site is a 404.

| App                  | Path                                       | Purpose                                                   |
| -------------------- | ------------------------------------------ | --------------------------------------------------------- |
| Marketing, port 3000 | `/`                                        | Template overview and waitlist form                       |
| Marketing            | `/waitlist/success`                        | Waitlist confirmation                                     |
| Marketing            | `/privacy`                                 | Privacy example; customize before collecting real signups |
| Dashboard, port 3001 | `/login`                                   | Google sign-in                                            |
| Dashboard            | `/`                                        | Protected todos, files, API keys, credits and email       |
| Dashboard            | `/checkout`                                | Protected Stripe test checkout                            |
| Dashboard            | `/checkout/success?session_id=cs_test_...` | Protected, server-verified payment status                 |
| Both apps            | `/error`                                   | Error-page preview; actual failures use the same UI       |
| Both apps            | Any unknown path                           | Custom page with HTTP 404 status                          |

The API runs on port 8787. Browsers normally call their own app's `/api/...` address, which forwards to the API Worker. This keeps login cookies on the dashboard's domain. You do not need to expose secrets to the browser.

## 3. Connect Google

Follow [Google sign-in](google-sign-in.md) to create or reuse a **Web application** OAuth client, register the local callback and add its ID and secret to `apps/api/.dev.vars`. That file is generated by `pnpm dev`, ignored by Git and read only by the backend. Keep its generated secrets.

Restart `pnpm dev`, open http://localhost:3001/login and choose **Continue with Google**. After sign-in, create a todo and upload a small file. Reload to check they persist. Download and delete the file when finished.

An agent can configure and test an existing authorized client, but the account owner may need to sign in or complete MFA first. Google's callback allowlist is separate from having a client ID and secret.

## 4. Add services as needed

| Service | Values you supply                                              | Setup                             | What to check                                                                       |
| ------- | -------------------------------------------------------------- | --------------------------------- | ----------------------------------------------------------------------------------- |
| Stripe  | Test secret and publishable keys from the same sandbox         | [Payment guide](payments.md)      | Test card succeeds, one credit pack is granted, success reload does not grant twice |
| PostHog | Public project token and regional ingestion host               | [PostHog guide](observability.md) | Opt in, visit pages, find events and a masked replay in that project                |
| Email   | A sender address on a verified Cloudflare email-enabled domain | [Email guide](data-and-email.md)  | Send to your own verified account address and check the inbox                       |

Use `.dev.vars` for backend credentials. `VITE_` variables are public frontend configuration, embedded in the build. Never put Google/Stripe secrets or a PostHog personal API key in them. The PostHog `phc_` collection token and Stripe `pk_test_` publishable key are designed to be public.

For pay per request, complete Stripe setup, choose **Add credits**, buy a test pack, then create a **Summary · 1 credit** key. The [metering guide](pay-per-request.md#try-it) has a copyable request and explains retries. A new account starts at zero credits. Cloudflare infrastructure billing is separate from the credits you charge your users.

## 5. Deploy to Cloudflare

Follow the [Wrangler deployment guide](manual-deployment.md). Use native Wrangler commands to create D1/R2 and Pages projects, configure their bindings and secrets, and deploy. Configure Google callbacks, Stripe prices/webhooks, PostHog and email through their provider tools when needed.

The API uses `apps/api/wrangler.json`; each website has its own Pages `wrangler.json`. Set the final URLs before building. Register the exact dashboard callback `https://YOUR-DASHBOARD/api/auth/callback/google` in Google, then complete a real sign-in. Use Cloudflare's Pages settings for custom domains and DNS.

## 6. Validate

```bash
pnpm validate
```

This runs lint, formatting, migration checks, unit/API tests, TypeScript, builds and browser flows in development and production runtimes. Temporary auth/payment/analytics fixtures need no provider accounts. Live Google consent, Stripe card completion, PostHog ingestion/replay and inbox delivery use the [verification checklist](verification.md).

Resource creation and deletion use provider tools. Keep the names and configuration of any deployed resources you own; local tests only clean up their own temporary local storage.

## Change it for your idea

- Page copy and routes: `apps/marketing/src/routes/` and `apps/dashboard/src/routes/`.
- Marketing name/URLs: `apps/marketing/.env.local` (see `.env.example`). Dashboard display name: `packages/shared/src/project.ts`.
- Database tables: `packages/data/src/schema.ts`; run `pnpm db:generate --name my_change`, review SQL, then `pnpm db:migrate` locally.
- REST inputs and responses: `packages/contracts/openapi/`; register new paths in `api.json`, then run `pnpm api:generate`. Keep private database rows out of public responses.
- UI components: import from `@workspace/shared`. Use Kumo's semantic styles and the shared page shells.
- Telemetry: `packages/observability/src/`. Keep user content and secrets out of events.

If ports 3000, 3001 or 8787 are busy, stop the other dev process before starting. If the waitlist cannot save, check http://localhost:8787/api/health and restart `pnpm dev`. Provider-specific troubleshooting lives in the linked guides.
